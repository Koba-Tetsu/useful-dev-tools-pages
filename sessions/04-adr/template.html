要約 ​

ADR の標準構成は Context / Decision / Consequences。各要素で何を書くか、具体的な指針を示します。

最小テンプレート ​

markdown
# ADR-001: タイトル（短く、判断を端的に）

## Context
- 問題は何か、なぜこの判断が必要だったか
- チームの制約・要件・前提条件
- 比較対象となった選択肢（2～3個を簡潔に）

## Decision
- 最終的に採用した案（何をするか）
- 簡潔な理由（1～2行）

## Consequences
- その決定で得られるメリット
- 注意すべき点、デメリット、リスク
- 実装や運用のポイント

各要素の詳細な書き方 ​

Context（背景・前提）を書くコツ ​

書くべき書かなくていい
なぜこの判断が必要なのか背景の全て
当時の制約や要件解決方法の詳細
比較対象となった選択肢長い歴史や文脈
チームのスキル/規模他部署のこと

悪い例：

パフォーマンス問題が起きたので、いろいろ検討しました。

良い例：

Context:
- DB クエリが大量で、レスポンス遅延（平均 500ms）
- ホットデータを繰り返しアクセスしている
- チームに Redis 経験者がいる
- 代替案：メモリキャッシュ、DB クエリ最適化、Read Replica

Decision（決定）を書くコツ ​

  1. 何をするかを明確に（選んだ案を一言で）
  2. 理由は簡潔に（1～2行、詳細は Consequences で）

悪い例：

Redis を採用します。

良い例：

Decision:
Redis をキャッシュレイヤーとして導入。  
理由：TTL 制御で古いデータを自動削除でき、追加実装がメモリキャッシュより簡単。

Consequences（帰結）を書くコツ ​

メリット（期待される効果）

  • レスポンスタイムが平均 500ms → 50ms に改善
  • スケーリング時も追加メモリで対応可能

デメリット／リスク（注意すべき点）

  • Redis サーバー管理の学習コスト
  • ネットワーク遅延がメモリキャッシュより発生

実装のポイント

  • TTL は 5 分に設定（古いデータリスクと負荷のバランス）
  • キャッシュ miss 時の DB 負荷急増に注意（キャッシュスタンピング対策）
  • モニタリング：Redis 容量使用率と eviction rate を監視

ファイル命名規則（推奨） ​

シンプル版（小チーム向け） ​

ADR-001-postgres-adoption.md
ADR-002-redis-caching-strategy.md
ADR-003-api-versioning.md

メタ情報付き版（大規模組織向け） ​

ADR-2024-01-15-001-postgres-adoption.md
ADR-2024-01-15-002-redis-caching-strategy.md

番号を振る理由：参照しやすく、歴史的順序が一目瞭然。

よくある書き間違い ​

❌ 間違い1：実装方法を書く ​

Decision:
Redis を使う。具体的には StackExchange.Redis ライブラリで、
ConnectionMultiplexer を作成して、IDatabase インターフェースを使う…

→ これは ADR ではなく設計書。ADR は「なぜ Redis か」に絞る。

❌ 間違い2：Context が長すぎる ​

Context: [5 ページの背景説明…]

→ 要件・制約・比較対象に限定。詳細は別ファイルにリンク。

❌ 間違い3：Consequences に メリットだけ ​

Consequences:
- スピードが速くなる
- スケーラブルになる

→ デメリット・リスク・注意点も必ず入れる。完璧ではないことを認める。

テンプレの最小例 ​

markdown
# ADR-001: PostgreSQL を採用

## Context
- トランザクション保証と耐障害性が必須
- チームに SQL 経験者がいる

## Decision
PostgreSQL を主要 DB として採用

## Consequences
- ACID 保証で既存システムの仕様要件を全て満たす
- 運用に PostgreSQL のバックアップ・レプリケーション自動化が必須
- 大規模トランザクションは別途性能調査が必要

このレベルで十分。完璧さは不要、判断の根拠が残ればOK。
