要約 ​

ADR（Architecture Decision Record）は「その判断をなぜしたか」を短く記録するドキュメント手法です。ソフトウェア開発における重要な判断の意図を残し、将来的に同じ判断の検証や変更判断を速くします。

本質：判断プロセスを記録する理由 ​

通常、重要な判断は以下のような背景で行われます：

  • 複数の選択肢がある（DB は PostgreSQL か MongoDB か、など）
  • トレードオフがある（スピード vs 耐障害性、など）
  • 当時の前提や制約がある（チームのスキル、プロジェクト規模、など）

しかし、その判断が記録されなければ：

  • 数ヶ月後に「なぜこうしているんだ」と思う
  • 新しいメンバーが同じ議論を繰り返す
  • 前提が変わったことに気づかず不適切な判断のまま続く

ADR はこのギャップを埋めます。判断した時点での背景・代替案・トレードオフを短く残すことで、将来の読者が判断の根拠を理解でき、検証や変更判断が迅速になります。

ADR の標準構成（三要素） ​

  • Context（背景・前提）: なぜこの判断が必要だったか、どんな制約や要件があったか
  • Decision（決定）: 最終的に選んだ案と、簡潔な理由
  • Consequences（帰結）: その判断で起こること、注意点、リスク、実装のポイント

他ドキュメントとの違い ​

ドキュメント目的対象更新頻度
設計書システム構成・仕様を説明現在の状態設計変更時
議事録議論や会議の内容を記録議論プロセスその場限り
ADR判断の根拠を記録決定の意図ほぼ不変（検証時のみ）

設計書は「現在どうなっているか」を説明し、議事録は「誰が何を言ったか」を残し、ADR は「なぜそうしたか」を残す点が特徴です。

ADR が向いている判断の種類 ​

技術・アーキテクチャ選定 ​

  • DB（PostgreSQL vs MongoDB vs Redis など）
  • 言語やフレームワーク（React vs Vue、Django vs FastAPI など）
  • キャッシュ戦略（メモリキャッシュ vs Redis、TTL 設定 など）

設計方針 ​

  • API バージョニング戦略（URL パス vs ヘッダー vs 共存 など）
  • 認証・認可の仕組み（JWT vs セッション、RBAC vs ABAC など）
  • エラーハンドリング（例外vs戻り値、エラーコード体系 など）

運用・プロセス ​

  • リリース戦略（カナリアデプロイ、ブルーグリーンデプロイ など）
  • バックアップ・復旧戦略（バージョニング、RPO/RTO など）
  • 監視・アラート設定（メトリクス選定、閾値 など）

共通点：決定が長期に影響し、後で質問されそうな、重要度が高い判断。

ADR が向かない判断 ​

  • 細かい実装（変数名、関数分割方法、フォーマット）
  • 毎日のように変わる設定（一時的なパフォーマンス調整値）
  • 自明な判断（仕様から自動的に決まる）
  • 可逆的な決定（簡単に戻せて、影響がない）

理由：過剰ドキュメント化によってメンテナンス負荷が増し、実務的でなくなります。
