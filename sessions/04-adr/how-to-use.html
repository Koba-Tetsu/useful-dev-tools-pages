要約 ​

ADR を無理なく運用するには、段階的に始めることが大切です。個人 → 小チーム → 全体組織という流れで徐々に広げるのが現実的です。

いつ書くか ​

  • 迷ったとき：複数の選択肢があり、トレードオフを感じるとき
  • 質問されそうなとき：「なぜこうしたの？」と後で聞かれそうな重要な判断
  • 長期影響があるとき：半年以上の間、影響し続ける判断
  • 前提が複雑なとき：理由が自明でなく、背景説明が必要なとき

逆に「いつも書く」というルールは避けましょう。書く価値がない小さい判断まで記録すると、ドキュメント負荷が増えて運用が続きません。

どの粒度で書くか ​

  • 目安：5～10分で書ける程度

    • 背景は「要件・制約」に限定（全部は書かない）
    • 決定は1～2行（選んだ案と理由）
    • 帰結は「影響と注意点」に限定

  • 構成例

    Context: 3～5行
Decision: 1～2行
Consequences: 3～5行
計10～12行程度が目安

  • 詳細は別置き

    • 実装詳細や設計図は ADR に書かず、別ファイルにリンク
    • ADR は「判断の理由」に集中

段階1：個人で始める（最初の1～2ヶ月） ​

  • 対象：個人が迷った重要な判断だけ
  • フォーマット：自由（完璧さは不要）
  • 保存：チームのドキュメントフォルダに ADR フォルダを作成
  • 目標：1ヶ月に1～2件書いてみる
  • 例：「キャッシュ戦略をどうするか迷った → ADR に残す」

段階2：小チーム（チーム内共有）で拡張（2～3ヶ月目以降） ​

  • 対象：チーム全体に影響する重要な判断
  • 形式：簡単なテンプレを決める（Context/Decision/Consequences）
  • 共有：PR に ADR ファイルを添える（レビュー時に背景を共有）
  • 命名：ADR-001-xxx.md と番号を振る
  • 頻度：重要度高い判断が出たときだけ（強制しない）
  • 例：「DB を PostgreSQL にするか MongoDB にするか → チーム内で ADR として共有」

段階3：組織全体（プロセス化） ​

  • 対象：会社全体で参考になる判断
  • ガバナンス：重要度に応じた簡易レビュー（強制ではなく）
  • アーカイブ：年1回、「この ADR の前提は今も有効か」を見直し
  • 学習：新しいプロジェクトで過去 ADR を参考にする文化

重要な注意：段階3 に急に進むと「完璧な記述」「承認フロー」化して、書く人の負担が増え、続きません。段階2 程度で十分という企業も多いです。焦らず、チームの実感に合わせて進めることが成功のコツです。

書き方と運用のコツ ​

背景（Context）を書くコツ ​

  • 要件・制約に限定（「どうやるか」は書かない）
  • 比較対象を明記（何と比較したか）
  • 当時のチーム規模やスキルレベルを簡潔に

決定（Decision）を書くコツ ​

  • 選んだ案だけを明確に
  • 簡潔な理由を1～2行で（詳細は Consequences で）

帰結（Consequences）を書くコツ ​

  • メリット（期待される効果）
  • デメリット（注意すべき点、リスク）
  • 次のステップ（設定値、導入方法など）

運用パターン例 ​

  • PR に ADR を添える：「DB 選定 PR に ADR-001 を添えてレビュー」
  • リファクタ時に参照：「古い設計を変更する前に ADR を確認」
  • 新プロジェクト開始時：「過去 ADR を参考に同じ判断は必要か確認」
