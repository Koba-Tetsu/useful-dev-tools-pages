要約 ​

短めの良い例と改善が必要な例を 5 種類示し、各々について「何が良いか」「何がダメか」を解説します。

例1：DB 選定（良い例） ​

markdown
# ADR-001: PostgreSQL を主要 DB として採用

## Context
- トランザクション処理とデータ整合性が必須要件
- 将来的な複雑なクエリが予想される
- チームに 3 人の SQL 経験者がいる
- 比較対象：MySQL（シンプル）、MongoDB（スケーラビリティ）

## Decision
PostgreSQL 14 を採用

## Consequences
- ACID 保証による強い一貫性が確保される
- JSON 型の拡張性が高い
- 運用にリポジトリ管理・バックアップ自動化が必須
- 読み取り負荷が高い場合は Read Replica を追加

何が良いか：

  • Background がクリア（なぜこの判断か分かる）
  • 代替案が明示（MySQL と MongoDB を検討したことが分かる）
  • Consequences に実装のポイント（Read Replica）がある

例2：DB 選定（ダメな例） ​

markdown
# ADR-001: Use PostgreSQL

We will use PostgreSQL for database.

何がダメか：

  • 背景が完全に不足（なぜ PostgreSQL？）
  • 比較対象が不明（他の選択肢が見えない）
  • 帰結がない（何に注意？）
  • 数ヶ月後「なぜ PostgreSQL にしたんだ」と質問される無限ループ

例3：API バージョニング戦略（良い例） ​

markdown
# ADR-002: API バージョニングは URL パスで実装

## Context
- API クライアントの互換性破壊頻度が高い（2～3ヶ月に1回）
- 複数バージョンの並行運用が必要
- 比較対象：URL ヘッダーバージョニング、段階的廃止

## Decision
`/v1/users`, `/v2/users` のように URL パスにバージョンを含める

## Consequences
- URL だけで API バージョンが判定でき、API ゲートウェイレベルでルーティング可能
- 古いバージョンの廃止予定を半年前に通知が容易
- URL が長くなる（微々たる影響）
- /v1 と /v2 の両方を運用するため負荷が 1.5 倍に

何が良いか：

  • Context が設計判断の背景を明確に
  • Consequences にトレードオフが両方ある（廃止通知が容易 vs 運用負荷増）

例4：キャッシュ戦略（良い例） ​

markdown
# ADR-003: Redis によるアプリケーション層キャッシュ

## Context
- ユーザープロフィール取得が全リクエストの 60%
- DB レスポンス平均 200ms → キャッシュで 20ms を目指す
- TTL 制御で古いデータを自動削除したい
- チームに Redis 経験者がいない

## Decision
Redis をキャッシュレイヤーとして導入

## Consequences
- キャッシュ hit 率が 80% 超で全体レスポンス 150ms に改善
- Redis サーバー運用の学習曲線（1ヶ月の習熟期間を想定）
- キャッシュ miss 時の DB 負荷急増対策（キャッシュスタンピング防止）
- TTL 5 分で設定（1 時間以上古いデータ配信はしない）
- モニタリング：容量使用率、eviction rate、キャッシュ hit rate を監視

何が良いか：

  • Context で学習コストまで記録（"チームに Redis 経験者がいない"）
  • Consequences で運用のリアルな課題（キャッシュスタンピング）を記録
  • TTL 値という実装値も含める

例5：テスト戦略（良い例） ​

markdown
# ADR-004: テスト戦略は段階式（ユニットテスト全数、統合テストは重要パス）

## Context
- テストスイート実行時間が 45 分で CI/CD パイプラインが遅い
- ユニットテストカバレッジ現状 75%、統合テスト 30%
- チームは 8 人で十分な テスト技術がある
- 完璧性 vs デリバリースピードのバランスが課題

## Decision
- ユニット　テスト：全メソッドで必須
- 統合テスト：決済・認認証など Critical path のみ

## Consequences
- CI/CD パイプライン時間が 45 分 → 12 分に短縮
- 回帰テストで漏れが増加するリスク（統合テストカバレッジ 30% のまま）
- 運用で統合テスト増のバランスを年 2 回見直し
- 新機能は統合テスト追加を義務化しない（developer 判断）

何が良いか：

  • Context に「完璧性 vs スピード」というトレードオフを明記
  • Consequences でリスク（漏れ増加）を認める
  • 定期的見直し（年2回）を仕込む

例6（おまけ）：テスト戦略（ダメな例） ​

markdown
# ADR-004: Test everything

We will write tests for all code.

何がダメか：

  • 「全部テストする」は現実的でない
  • パフォーマンス（45分問題）への言及がない
  • Consequences がない（何が起こる？）
  • 実行不可能なルールは運用で無視される

実装例を取り入れるコツ ​

ADR を書く際は「同じような判断」の過去 ADR を参考にしましょう：

  • DB 選定 → ADR-001 を読んで同じ構成で書く
  • API 設計 → ADR-002 を参照
  • キャッシュ戦略 → ADR-003 を参照

このように例が蓄積されると、新しい判断が速く、品質も高くなります。

初心者向け：最小限の ADR（3行版） ​

「長文は大変...」という方へ。最小限で有効な ADR がこちら：

markdown
# ADR-005: [決定内容]

## Context
[なぜこの判断が必要か？ 1～2文]

## Decision
[何を決めるか？ 1文]

## Consequences
[その結果、何が起こる？ 1～2文]

最小限の例：

markdown
# ADR-005: API 通信は GraphQL にする

## Context
REST API だとエンドポイント増加で管理が煩雑になってきた。

## Decision
GraphQL を採用する

## Consequences
クライアント側で必要なデータだけ取得でき、オーバーフェッチが減少。サーバー側は resolver 実装と GraphQL スキーマ設計が必須。

ここまで最小限なら、重要度が高い判断は 15 分で書けます。
